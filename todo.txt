TRADING ENGINE - THINGS TO FIX BEFORE PRODUCTION
====================================================
(Written in plain language so you can pick this up later)

--------------------------------------------------
THE 2 MOST URGENT THINGS (do these first)
--------------------------------------------------

1) YOUR SECRET KEY IS LEAKED IN GIT HISTORY
   What's wrong:
   - Your .env file (which has JWT_SECRET="THISOKAS") got committed to git.
   - Anyone who can see your repo history can fake login tokens for ANY user.

   What to do:
   - Add .env to .gitignore right away.
   - Remove .env from git history completely (not just delete it now -
     it's still in old commits). Look up "git filter-repo" or "BFG Repo
     Cleaner" to scrub it from history.
   - Generate a new, long, random JWT_SECRET (don't reuse "THISOKAS").
   - Never commit real secrets again - use .env.example with fake
     placeholder values instead.

2) MONEY MATH USES FLOATING POINT NUMBERS (f64)
   What's wrong:
   - Your database stores balances as NUMERIC (correct, exact numbers).
   - But your Rust code converts everything to f64 (decimal numbers that
     computers store imprecisely) to do the math, then saves it back.
   - Over time, tiny rounding errors will build up and balances will
     become slightly wrong. This is a classic "invisible bug" that only
     shows up after real usage.

   What to do:
   - Use a proper decimal/money type in Rust instead of f64
     (look up the "rust_decimal" crate, or sqlx's "bigdecimal" feature).
   - Do all balance math using that type, not plain floats.

--------------------------------------------------
OTHER MONEY-SAFETY PROBLEMS
--------------------------------------------------

3) TWO ORDERS AT THE SAME TIME CAN OVERSPEND A USER'S BALANCE
   What's wrong:
   - When someone places an order, you check "do they have enough
     balance?" and THEN later you deduct it. Nothing stops two orders from
     both passing the check before either one deducts money.
   - Example: user has 100 rupees, places 2 orders of 80 rupees each at
     the exact same time -> both could be approved before either debits
     the balance -> user "spends" 160 rupees they didn't have.

   What to do:
   - Do the balance check and the balance deduction as ONE atomic
     database operation (e.g. UPDATE ... WHERE balance >= amount, and
     check if a row was actually updated), or lock the user's balance row
     while you check and update it.

4) NO DATABASE TRANSACTIONS ANYWHERE
   What's wrong:
   - Settling a trade involves several separate steps: insert the trade,
     update buyer balance, update seller balance, mark old order as
     fulfilled, insert new resting order.
   - Right now these are separate, unconnected database calls. If your
     server crashes or a query fails halfway through, you can end up with
     a trade recorded but balances not updated (or vice versa) - a
     half-finished, broken state.

   What to do:
   - Wrap all these steps in a single database transaction
     (BEGIN ... COMMIT). If any step fails, the whole thing rolls back
     and nothing is left half-done.

--------------------------------------------------
MATCHING ENGINE (ORDER BOOK) BUGS
--------------------------------------------------

5) ORDERS AREN'T MATCHED BY BEST PRICE FIRST
   What's wrong:
   - A real exchange matches the BEST available price first (cheapest
     ask for buyers, highest bid for sellers).
   - Your code just loops through the orders in the order they were
     added, and matches whichever one it reaches first that qualifies -
     not necessarily the best price. So a trader could get a worse deal
     than they should.

   What to do:
   - Keep your bids sorted highest-price-first, and asks sorted
     lowest-price-first (a sorted list, or a proper priority
     queue/heap).
   - Always match against the front of that sorted list first.

6) OLD FULFILLED ORDERS NEVER GET CLEANED OUT OF MEMORY
   What's wrong:
   - When an order is fully filled, you just mark it "fulfilled" and
     skip over it - but it stays in the list forever.
   - Over time this list keeps growing and the matching engine has to
     scan through more and more dead orders, getting slower and slower.

   What to do:
   - Actually remove fulfilled orders from the in-memory list once
     they're done (not just mark and skip).

7) A REGULAR LOCK (MUTEX) IS HELD WHILE WAITING ON THE DATABASE
   What's wrong:
   - Your code locks the order book, then does slow database work
     (settling the trade) WHILE STILL HOLDING THAT LOCK.
   - This means only one order can be processed at a time across your
     WHOLE app, even though database calls are slow. It kills your
     throughput and is a known trap in async Rust code.

   What to do:
   - Restructure so you: (a) lock the order book only briefly to run the
     matching logic, (b) unlock it, (c) then do the slower database
     settlement work without holding the lock.
   - If you do need an async-aware lock, use "tokio::sync::Mutex" instead
     of the standard library one - but the better fix is the
     restructuring above.

--------------------------------------------------
THINGS THAT ARE MISSING ENTIRELY
--------------------------------------------------

8) NO TESTS
   - There isn't a single automated test for the matching engine,
     settlement logic, or auth. For something handling real money, this
     is risky - you want tests that check things like "does a partial
     fill work correctly", "does balance math stay correct after 1000
     trades", etc.

9) NO RATE LIMITING
   - Nothing stops someone from spamming your login or order endpoints
     as fast as they want. Add rate limiting, especially on
     /api/login and /api/register.

10) NO LOGGING / MONITORING
    - There's basic eprintln! in a couple of places but no real
      structured logging or tracing. If something goes wrong in
      production, you'll have a hard time figuring out what happened.
      Look into the "tracing" crate.

11) SEVERAL .unwrap() CALLS THAT CAN CRASH THE SERVER
    - A few places assume something always works (like reading a value
      out of a request) and just .unwrap() it. If that assumption is
      ever wrong, it crashes that request instead of failing gracefully.
      Replace these with proper error handling.

--------------------------------------------------
SMALL / COSMETIC CLEANUP
--------------------------------------------------

12) Two stray files at the root of your project ("2" and ":w") - these
    look like an accidental save from vim. Safe to delete.

13) Your qty and price for orders are whole numbers (integers) only, so
    you can't trade fractional amounts (like 0.001 BTC). Decide if this
    is intentional (e.g. trading in smallest units) or a limitation you
    want to fix later.

--------------------------------------------------
SUGGESTED ORDER TO TACKLE THIS
--------------------------------------------------
1. Scrub the leaked secret from git history + rotate it        (#1)
2. Switch money math from f64 to a decimal type                (#2)
3. Wrap settlement steps in a database transaction              (#4)
4. Fix the balance check race condition                         (#3)
5. Fix order matching to use best-price-first                   (#5)
6. Stop holding the mutex across database calls                 (#7)
7. Clean up fulfilled orders from memory                        (#6)
8. Add tests as you fix each piece above                        (#8)
9. Add rate limiting + logging                                  (#9, #10)
10. Replace risky .unwrap() calls                                (#11)
11. Cosmetic cleanup                                             (#12, #13)

Good luck! This is a solid learning project - the shape of the system
(auth -> orders -> matching -> settlement) is right, it just needs the
money-safety and correctness pieces tightened up before it could handle
real funds.
